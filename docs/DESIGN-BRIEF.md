# Design brief — grocery billing POS (shared context for sub-agents)

Read this before your task. Do not edit this file.

## Product

Offline-first grocery billing POS. Records every bill; reports per item per day and per month. **No payments**
(no tenders, no cash sessions, no refunds in v1). Replaces GoFrugal for an Indian grocery chain with multiple
stores per enterprise.

## Stack

- Terminal: Wails v3 + Go, React + TypeScript + shadcn/ui, local SQLite (WAL, `modernc.org/sqlite`),
  `synchronous=FULL` on the billing connection. Measured: NORMAL wrote 1,235 bills/s, FULL about 41 on the same
  VM. A bill that survives a power cut is worth 30x the write cost.
- Cloud: Cloudflare Worker (Hono, TypeScript) + D1. **One Worker serves every tenant, routed by Host; one D1
  database per enterprise.** Workers Paid is required (Free quotas and the 500 MB cap are not enough).
- Wire: REST + JSON, `/v1/...`, batches.
- Tooling: Bun for installs/scripts. Workers run on workerd.

## Domain shapes already decided

- Quantities are integers in base units (grams, millilitres, pieces). Convert for display only.
- Money is integer minor units (paise).
- `items`: id (client UUID), name, name_local, dimension (mass|volume|count), pricing_mode
  (`fixed_only` | `tiered` | `linear`), base_unit, default_sales_unit, tax_rate_id, flags
  (allow_discount_pct, restrict_price_edit, prompt_qty, scale_qty), active, updated_at.
- `item_prices(item_id, qty_base, price_minor, version, store_id NULL, valid_from, valid_to)`: SCD2 history,
  server clock for `valid_from`. `store_id NULL` = franchise default, non-null = store override.
- `item_identifiers(alias, kind, item_id, qty_base NULL, store_id, active)`: kind is
  `alias | sku | ean | plu`. Alias normalised (trim, uppercase), unique per store, exact match wins.
- `units(unit, group, precision, factor_to_base)`; `tax_rates(id, name, rate_bp, active)`.
- `bills`: id UUIDv7, store_id, terminal_id, user_id (cashier), auth_method, shift_id, business_date,
  local_seq, display_no, invoice_no, total_minor, rounding_minor, created_at (terminal clock),
  received_at (server clock), synced_at, voided. Bills are immutable; corrections are void records.
- `bill_lines`: bill_id, item_id, item_name, dimension, qty_base, price_version, price_source
  (`list|tier|override|manual`), list_price_minor, price_minor, price_breakdown JSON, line_total_minor,
  tax_rate_bp, cgst_minor, sgst_minor, cess_minor, override_by, override_reason, override_note,
  policy_violation. Name and price are copied onto the line; reports never recompute from `item_prices`.
- Hedges agreed with the BRD: `inventory_movements`, `shifts`, `numbering_policy`,
  `store_settings(business_day_start_minutes, rounding_mode)`, `audit_events`, `terminal_config`.

## Sync contract (critical)

- Terminals send a **checkpoint** (`since`) with every catalog pull: "give me everything that changed after
  this point". The checkpoint must be monotonic, gap-free, and cheap to index.
- Bills push in batches of at most 100 bills per request, one `db.batch()` per bill, lines and movements before
  the header. The Worker inserts `ON CONFLICT(id) DO NOTHING` and returns the accepted ids; the terminal marks
  only those as synced. Per-row `synced_at`, not a high-water mark. The whole request stays under 1,000 D1 calls.
- Staff sessions go up before bills, as a close-only upsert in `started_at` order. A bill outside every session
  is accepted and flagged `unverified_staff`, never rejected: the server must not abort a sale the shop made.
- A void is `POST /v1/bills/:id/void`, or a `voids[]` entry on the same push. `bill_voids` is the record; a
  trigger flips the bill and decrements the daily rollup in the same statement. A void for an archived bill is
  parked `bill_archived`, never dropped.
- Unique `(store_id, terminal_id, local_seq)` on the server is the second line of defence.
- Retry: exponential backoff with jitter. Refused bills are parked, not hammered.
- Catalog pull order: refresh token, push bills, pull catalog, advance checkpoint only after the transaction
  commits.
- Stale price detection: Worker compares each line's `price_version` to the version valid at `created_at`
  and sets `stale_price`. Diagnostic only, never rewrites money.

## Auth and tenancy

- One Worker for every tenant, routed by `Host` compiled from `infra/tenants.json`. Unknown host is
  `421 unknown_host`. The tenant's binding supplies the D1 handle; `schema_meta.tenant_id` must match the routed
  tenant (`503 tenant_mismatch`). Nothing about tenancy comes from a request body or an environment constant.
- Device plane: device credential in the OS keychain exchanged for a 5 min JWT (`typ: "device"`, `scope: "sync"`,
  `tenant_id`, `aud: app_id`). The signing key is derived per tenant; the header `kid` picks it, and the key is
  never derived from a claim. No refresh token. Billing never touches the token.
- Admin plane: **Better Auth** (email/password, Google OAuth, TOTP) over its own `auth_*` tables, one instance
  constructed per request. HttpOnly session cookie, 12 h sliding with a 30-day absolute cap. Roles (`owner`,
  `staff`, `cashier`) and `user_stores` scoping stay ours. Cashiers have no `auth_user` row, which is what keeps
  them out of the admin web.
- Cashiers are `users` rows with a PIN in `staff_credentials`, verified offline for attribution; `bills.user_id`,
  `bills.auth_method` (`password|pin_offline`) and `bills.staff_session_id`. Approvals that gate money use
  online-minted `approval_grants`, not cached manager PINs.
- Enrolment is two-step: `/v1/enroll` creates a pending device, `/v1/token` returns `403 approval_pending` until
  the owner approves it in admin. `install_id` in the keychain detects a cloned disk.

## Cloudflare constraints to respect

- D1 is SQLite: one writer per database, 10 GB per database (a paid-plan ceiling, not a soft one), batch
  statements for atomicity, no interactive transactions across requests, limited query duration, no filesystem.
- One Worker invocation may make 1,000 D1 API calls; a `db.batch()` counts as one call whatever it contains.
  Measured on D1: 1,000 single queries pass, 1,001 fail; one batch of 5,000 statements passes.
- Workers have CPU limits and no persistent connections. KV for cheap caches, Queues for async work if needed.
- Compute is pooled, data is sharded: one Worker, one database per enterprise, stores as rows. The only
  exception is a contracted per-tenant Worker (D20) for an enterprise that outgrows the default.
- Archival to R2 is a v1 feature, not a later optimisation (D22). A realistic 4-line bill is 4,961 bytes on D1;
  five stores at 600 bills a day reach 10 GB in about 1.8 years without it.

## Non-goals for v1

Purchases, suppliers, stock ledger enforcement, transfers, loyalty, customers/credit, tenders/payments,
returns/refunds UI, batch/serial tracking, report builder, e-invoice.
